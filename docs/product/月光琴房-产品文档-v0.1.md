> 版本：v0.1 讨论稿
> 更新日期：2026-08-31
> 产品阶段：概念验证 / 核心练习体验定义
> 最终目标设备：iPad
> 第一阶段验证环境：桌面 Chrome Web 应用，界面优先适配 iPad 横屏
> 第二阶段产品形态：核心功能验证通过后，开发 iPad 原生应用
> 文档依据：当前产品原型、Duolingo Music 参考图及本轮产品讨论

## 1. 产品摘要

### 1.1 一句话定义

**月光琴房是一款面向钢琴零基础用户的游戏化练习产品，通过“节奏色块 → 琴键定位 → 识谱 → 指法 → 单手 → 双手大谱表”的渐进式训练，帮助用户最终完整弹奏《梦中的婚礼》。**

### 1.2 产品承诺

用户不需要先学完一整套枯燥乐理，也不需要在第一次练习时同时理解节奏、音高、指法和双手配合。产品每次只增加一个认知变量，用短小、容易成功的挑战，让用户持续感受到：

- 我知道下一步该做什么；
- 我刚刚确实进步了；
- 我离完整弹奏目标曲又近了一小段。

### 1.3 最终用户结果

完成核心课程后，用户应能够：

1. 识别《梦中的婚礼》所需的基础节奏与常用音符；
2. 在键盘上找到对应琴键，并采用合理的基础指法；
3. 分别完成右手旋律和左手伴奏；
4. 阅读高音谱表与低音谱表组成的大谱表；
5. 以适合初学者的稳定速度完成双手合奏；
6. 最终脱离大部分颜色、字母和动态提示，完整演奏目标曲。

### 1.4 产品交付路线

#### 第一阶段：Chrome Web 核心验证

Web 版本是低成本、快速迭代的产品验证载体，不是最终交付形态。

- 使用桌面 Chrome 开发、调试和演示；
- 页面尺寸、信息密度和交互优先按 iPad 横屏设计；
- 所有主要操作采用触控友好的方式，不依赖悬停和精确鼠标操作；
- 验证节奏色块、动态乐谱、虚拟键盘、指法、单手/双手和反馈闭环；
- 可在桌面 Chrome 中验证 MIDI 键盘输入，但不把浏览器差异当作产品能力；
- 快速进行目标用户测试，用数据决定是否进入原生开发。

#### 第二阶段：iPad 原生应用

当核心教学机制和练习闭环通过验证后，开始开发正式 iPad 原生应用。

- 继承已验证的课程结构、视觉语言和交互模型；
- 在真实 iPad 上完善触控、音频、设备连接、离线能力和系统集成；
- 重新实现对实时性要求较高的练习引擎，而不是简单把 Web 页面套进原生容器；
- Web 阶段产生的课程数据结构、谱面模型和评分规则应尽量设计为可迁移资产。

## 2. 背景与机会

### 2.1 初学钢琴的真实难点

传统入门练习经常要求用户同时处理多个问题：

- 看懂五线谱；
- 找到琴键；
- 判断节奏和时值；
- 选择正确手指；
- 控制左右手；
- 跟上固定速度；
- 在犯错后继续演奏。

这会快速消耗工作记忆。用户往往不是“不适合学钢琴”，而是一次被要求学习了太多事情。

### 2.2 Duolingo Music 的启发

参考产品最值得借鉴的不是表面的颜色或游戏化积分，而是它对学习负担的拆分：

- 最基础挑战不显示传统音符，而用彩色矩形表示出现时机和持续时间，让用户先学习节奏；
- 乐谱内容从右向左移动，用户只需关注固定判定线附近即将到来的内容；
- 乐谱与可操作琴键位于同一练习界面，视觉与动作直接对应；
- 练习很短、反馈即时，失败成本低；
- 音符、字形和颜色形成统一、友好的产品语言。

### 2.3 月光琴房的差异化机会

Duolingo Music 更擅长基础识别和节奏练习，但未充分解决真实钢琴学习中的两类核心问题：

1. **双手合奏与大谱表阅读；**
2. **面向零基础用户的指法与手型引导。**

因此月光琴房的核心差异化不是“做一个更像 Duolingo 的界面”，而是把其低门槛学习方法延伸到可迁移的钢琴演奏能力。

## 3. 目标用户

### 3.1 核心用户

- 从未系统学习过钢琴；
- 可能不认识五线谱；
- 使用 iPad 学习，有电子琴、数字钢琴，或暂时只使用屏幕键盘；
- 想快速弹会一首熟悉、好听、有成就感的曲子；
- 每天可练习约 10–30 分钟；
- 容易因枯燥理论、连续失败或进步不可见而放弃。

### 3.2 核心使用任务

> 当我想学会一首真正喜欢的钢琴曲时，我希望产品每天告诉我一个足够简单的练习任务，并在我弹奏时立即帮助我纠正问题，让我不需要先成为乐理专家，也能逐步完成整首曲子。

### 3.3 非目标用户（当前阶段）

- 需要专业考级体系或高级演奏技巧的用户；
- 需要系统覆盖大量曲目的音乐学院学生；
- 需要教师排课、班级管理或机构后台的用户；
- 期待产品完全替代真人教师进行高级手型纠正的用户。

## 4. 产品定位与设计原则

### 4.1 产品定位

**30 天单曲目标教练，而不是一开始就做完整的在线钢琴学校。**

《梦中的婚礼》是明确、可展示、可完成的学习终点。课程、反馈、激励和数据都应服务于“今天离完整演奏更近了吗”。

### 4.2 核心原则

#### 原则 A：先演奏，再解释

先让用户在低认知负担下完成动作并听到结果，再逐步引入术语和乐理。

#### 原则 B：一次只增加一个变量

节奏、音高、琴键位置、音符、指法、左手、右手和双手不应在第一节课同时出现。

#### 原则 C：乐谱是可交互的时间轴

乐谱不是静态图片。它应当移动、响应、等待、减速，并明确告诉用户“现在”和“接下来”。

#### 原则 D：反馈必须可行动

不只显示“错误”，而应说明是音高、时机、时值还是双手不同步，并给出下一次可执行的修正提示。

#### 原则 E：辅助信息逐步淡出

颜色、字母、琴键高亮和指法是脚手架，不是永久依赖。随着熟练度提高，系统应逐层减少提示。

#### 原则 F：真实演奏能力高于游戏分数

连胜、经验值和等级用于促进练习，不应鼓励用户通过反复点击简单题绕过真正的演奏目标。

## 5. 核心教学模型

### 5.1 信息渐显路径

| 阶段 | 乐谱呈现 | 键盘呈现 | 学习目标 | 主要反馈 |
|---|---|---|---|---|
| 0. 纯节奏 | 彩色矩形，不显示音符 | 简化按键或任意键 | 拍点与时值 | 早、准、晚；按住时间 |
| 1. 琴键定位 | 色块增加用户选择的音名 | 对应琴键高亮 | 声音与位置映射 | 按对琴键、反应时间 |
| 2. 指法建立 | 色块显示 1–5 指法 | 指尖位置或手型提示 | 用正确手指准备和落键 | 建议指法，不做强制判错 |
| 3. 音符渐显 | 色块逐步转为产品化音符 | 保留所选音名与颜色 | 建立图形与音高映射 | 音高、节奏、时值 |
| 4. 单手乐句 | 标准化单谱表，保留必要提示 | 右手或左手音区 | 完成短乐句 | 连贯度、换位、稳定性 |
| 5. 双手合奏 | 高低音大谱表 | 双手音区与联合提示 | 左右手同步 | 分手结果、同步偏差 |
| 6. 完整演奏 | 接近标准乐谱，辅助最少 | 可隐藏虚拟键盘 | 完整弹奏目标曲 | 章节表现与整体复盘 |

### 5.2 辅助淡出规则

同一小节连续稳定完成后，系统依次减少：

1. 琴键强高亮；
2. 音名字母；
3. 全量指法数字；
4. 音符颜色；
5. 节奏吸附或等待；
6. 虚拟键盘。

当用户表现明显下降时，可临时恢复上一层提示，但不应直接把用户退回整章。

### 5.3 音名显示规则

- 内容数据内部统一使用标准音高标识，例如 `C4`、`D4`，作为乐谱、键盘、MIDI 和评分之间的稳定映射；
- 用户界面默认显示 `C / D / E`，用户可以切换为 `do / re / mi`；
- 首次建立音高映射时，可以短暂显示 `C（do）` 形式的双标提示；
- 用户建立映射后，只显示其选择的一套音名，双标不作为长期默认状态；
- 音名与指法数字 `1–5` 必须具有清晰的视觉层级，避免将音高和手指编号混淆；
- 随着识谱能力提升，音名按照 5.2 节的规则逐步淡出，最终以五线谱位置完成识别。

## 6. 核心练习交互

### 6.1 练习界面结构

练习页应以两个核心区域为中心：

- **上半区：动态乐谱 / 节奏轨道；**
- **下半区：可交互钢琴键盘。**

顶部保留简洁的关卡进度与退出入口。当前练习中不应同时展示大量课程地图、统计卡片和非必要导航，以减少注意力竞争。

### 6.2 iPad 使用形态

- **横屏是核心练习的标准方向。** 横向空间同时承载动态乐谱、大谱表和足够宽的虚拟键盘；
- **竖屏用于轻量浏览。** 学习地图、今日目标、复盘和设置可以支持竖屏，但进入正式练习时应引导用户横屏；
- Chrome Web 原型在 iPad 横屏视口下开发和验收，视觉与交互不得以桌面宽屏为默认；
- 练习界面以触控为第一输入方式，主要操作必须适合双手快速点击，不能依赖鼠标悬停；
- 支持把 iPad 放在钢琴谱架上使用，重要信息应集中在屏幕中上部，避免操作区被琴键或手掌遮挡；
- 适配不同尺寸 iPad、安全区域、横屏方向切换与系统多任务状态；
- 练习过程中应防止误触退出，并避免自动锁屏打断长乐段；
- 外接电子琴时，iPad 主要承担乐谱、节拍、反馈和课程引导；没有电子琴时，屏幕下半区承担可演奏键盘。

### 6.3 固定判定线与右向左运动

- 判定线固定在屏幕左侧约 25%–30% 的位置；
- 色块或音符从右向左移动；
- 用户主要关注判定线附近，而不需要追踪整屏乐谱；
- 音符到达判定线时触发应演奏时机；
- 正确演奏后音符产生简短确认反馈并离开；
- 下一组音符始终在右侧可预见范围内。

### 6.4 速度模式

#### 学习模式

- 用于首次学习新音、琴键位置、指法和手位；
- 目标音到达判定线后可以完全停住，用户按对后再继续；
- 允许用户“按自己的节奏弹”，主要目标是完成动作并建立正确映射；
- 纯节奏训练不使用完全等待机制。

#### 跟随模式

- 用于节奏色块、已经学过的乐句和从分手到合手的过渡练习；
- 乐谱维持可调节的低速连续节拍，不因单次错误暂停；
- 错误不会立刻中断整段；
- 结束后针对困难小节再练。

#### 演奏模式

- 乐谱按目标速度连续移动；
- 漏音、错音或节奏偏差只被记录，不中断演奏；
- 仅提供必要提示；
- 用于整段或整曲验收。

模式选择由当前练习目标决定，而不是只由用户水平决定：学习新动作时等待，训练节奏时保持连续，完整演奏时不中断。

### 6.5 输入方式

#### MVP 建议

1. iPad 屏幕虚拟键盘：覆盖无乐器用户、最早期课程和随时练习场景；
2. 触控节奏板：在纯节奏课程中减少对具体琴键的干扰；
3. 桌面 Chrome Web MIDI：在用户授权后连接 MIDI 键盘，用于提前验证真实琴键输入和评分逻辑；
4. 鼠标点击只作为开发便利，不作为主要交互设计依据。

#### 浏览器验证边界

桌面 Chrome 支持 Web MIDI，但需要安全上下文和用户明确授权。该能力适合验证 MIDI 输入、节奏判定和真实琴键练习流程。

当前处理原则：

- Web 阶段确定支持虚拟键盘和触控节奏板；
- 桌面 Chrome 的 Web MIDI 是验证工具，也是 Web 原型的增强能力；
- 所有主线关卡和章节验收均可通过 iPad 屏幕键盘完成，MIDI 不是解锁条件；
- 屏幕键盘与 MIDI 使用同一套课程路径、进度和基础通过标准，不建立两套课程；
- 章节解锁进度在两种输入方式之间共享，但每次成绩明确标记为“屏幕完成”或“MIDI 完成”，最佳记录按输入方式分别展示；
- MIDI 可额外记录力度和实体踏板数据，但这些增强数据在验证期不影响关卡解锁；
- Chrome Web MIDI 的验证结果不能直接代表 iPad 浏览器能力；
- 最终 iPad 应用的真实设备输入在原生阶段重新设计和验证；
- 麦克风识音暂不进入核心 Web 验证范围，除非用户研究证明原声钢琴输入是首发刚需。

Web 阶段结束前仍需在真实 iPad 上进行布局、触控姿态和可读性检查，但浏览器原型不承担最终原生应用的性能验收。

#### 后续能力

- 麦克风识别原声钢琴音高；
- 摄像头辅助观察手型和指法；
- 外接踏板与力度数据分析。

> 说明：普通 MIDI 能识别音高、开始时间、持续时间和部分力度信息，但无法知道用户具体使用了哪根手指。因此 MVP 中指法属于引导与自我确认，不应伪装成系统可准确检测的评分项。

## 7. 练习类型

### 7.1 节奏色块

**目标：** 在不识谱的情况下理解拍点和长短。

- 色块位置代表出现时间；
- 色块长度代表持续时间；
- 初期可使用任意指定琴键或单一琴键；
- 成功反馈强调节奏准确，而非音符知识。

### 7.2 听后模仿

**目标：** 建立声音、琴键位置和短期音乐记忆。

- 系统先演奏 2–5 个音；
- 用户按相同顺序复现；
- 可从只显示琴键提示，逐渐过渡到只听声音。

### 7.3 琴键定位

**目标：** 快速找到指定琴键。

- 提示音名、颜色或目标声音；
- 用户点击虚拟琴键或真实琴键；
- 优先训练目标曲实际使用的音域。

### 7.4 单手跟弹

**目标：** 完成右手旋律或左手伴奏的短乐句。

- 右手与左手采用可区分但和谐的视觉编码；
- 提示即将发生的换位；
- 支持循环 1–2 小节；
- 可调节速度和提示强度。

### 7.5 双手对齐

**目标：** 理解两只手在同一时间轴上的配合。

- 使用大谱表；
- 高音谱表对应右手，低音谱表对应左手；
- 两行谱表共享同一条垂直判定线；
- 垂直对齐的音符代表同时落键；
- 可选择右手、左手或双手模式；
- 反馈分别显示右手、左手和同步偏差。

### 7.6 困难小节循环

**目标：** 把错误转化成短而明确的专项练习。

- 自动识别连续出错或明显降速的小节；
- 将其拆为 10–30 秒循环；
- 先降速、恢复辅助，再逐步增加速度；
- 达标后无缝回到原乐段。

### 7.7 完整演奏

**目标：** 从局部技能迁移到完整作品。

- 必须在演奏模式中从头到尾完成目标版本，不能跳过乐段、等待用户或中途重新开始；
- 必须完成目标版本规定的左右手音符；
- 演奏结束后再展示整体复盘；
- 报告按章节定位问题，而不是只给一个总分；
- 支持保存最佳完成记录。

完整演奏采用多维硬性门槛和三级结果，某一项明显不足不能通过其他项目的高分抵消：

| 等级 | 完整性与连续性 | 音符正确率 | 节奏达标率 | 速度要求 |
|---|---|---:|---:|---:|
| 完整弹会 | 完成全部约 35 小节，双手演奏且不中断 | ≥ 90% | ≥ 80% | ≥ 参考速度的 70% |
| 熟练演奏 | 满足完整弹会条件 | ≥ 95% | ≥ 90% | ≥ 参考速度的 90% |
| 舞台时刻 | 目标速度完整演奏，并进一步关注稳定性与音乐表现 | 在熟练演奏基础上持续优化 | 在熟练演奏基础上持续优化 | 参考速度的 100% |

上述百分比是验证期初始阈值，可根据真实用户数据校准；完整性、连续性、双手要求和多维门槛结构保持不变。由于屏幕键盘无法可靠识别真实手指、力度和踏板，验证期不把这些项目作为“完整弹会”的硬性条件。

## 8. 指法与手型系统

### 8.1 基础规则

- 采用钢琴通用指法编号：拇指为 1，小指为 5；
- 右手指法显示在高音谱表音符上方；
- 左手指法显示在低音谱表音符下方；
- 只强强调即将使用或发生变化的指法；
- 重复音型不需要为每个音永久显示数字。

### 8.2 新手视觉提示

指法提示采用三级优先级，按用户当下需要逐层介入：

1. **主要实时提示：琴键高亮与指法数字。** 即将演奏的琴键显示“指尖光点”和建议指法，并与乐谱中的目标音同步；这是练习过程默认使用的提示。
2. **手位变化提示：小型手型示意。** 仅在首次建立手位、发生换位或需要跨指时出现，同时提前标出新的拇指位置，避免持续占据练习界面。
3. **难点示范：可主动查看的短视频。** 用于解释跨指、换指或特殊手型等静态图难以说明的动作，不在乐谱滚动过程中持续播放，也不作为完成普通练习的必要步骤。

系统支持“全部指法 / 仅变化指法 / 隐藏指法”三档显示，并随着熟练度逐步减少提示。

### 8.3 反馈边界

- 未接入摄像头或专用传感器时，不对真实使用手指做自动判定；
- 系统可以判断用户是否按对音、节奏和时值；
- 指法提示应使用“建议使用 3 指”，而不是在无检测依据时声称“你用了错误手指”。

---

## 9. 大谱表与双手练习模型

### 9.1 显示规则

- 高音谱表与低音谱表始终共享时间轴；
- 右手和左手可以使用不同强调色，但不能依赖颜色作为唯一识别方式；
- 当前需要演奏的两手信息同时靠近判定线；
- 和弦或双手同步点应形成清晰的纵向视觉关系；
- 初期可放大谱表间距，熟练后逐渐接近标准排版。

### 9.2 分手到合手的过渡

每个双手乐段遵循：

1. 右手单练；
2. 左手单练；
3. 双手分层预览；
4. 双手低速、可等待练习；
5. 双手连续跟随；
6. 接近目标速度演奏。

系统应记录每只手的熟练度，避免用户右手已熟练却被迫重复同等强度的右手课程。

## 10. 反馈与评分

### 10.1 单音反馈维度

- **音高：** 是否按对目标音；
- **时机：** 早、准或晚；
- **时值：** 是否按得过短或过长；
- **力度：** 设备支持时作为进阶反馈；
- **同步：** 双手或和弦是否同时落键。

### 10.2 反馈表达

优先使用直接、可行动的语言：

- “这个音早了一点，再等它到达光线。”
- “左手正确，右手晚了半拍。”
- “音按对了，再多保持一点。”
- “这里要换到 3 指，下一次会更顺。”

避免只显示红叉、失败音效或抽象分数。

### 10.3 容错策略

- 初级练习使用较宽的判定窗口；
- 第一次错误优先给提示，不立即中断；
- 连续错误时自动减速或暂停；
- 结束后只选择最值得修正的 1–2 个问题；
- 用户可一键重练困难小节。

### 10.4 结果页

结果页应回答三个问题：

1. 我完成了什么？
2. 我比上次进步在哪里？
3. 下一次只需要改进什么？

建议展示：当前演奏等级、完整性、连续性、速度、节奏稳定性、正确音符率、双手同步度、最值得重练的小节，以及距离下一级标准的差距。结果页不使用单一总分掩盖未达标维度。

## 11. 课程结构

> 课程章节、乐段划分和逐关卡设计由独立的[《月光琴房课程与关卡设计文档 v0.1》](../curriculum/月光琴房-课程与关卡设计文档-v0.1.md)承接；本章只保留产品级课程框架。

### 11.1 课程主线

当前产品原型中的七阶段可继续作为高层路线，但内部应按真实技能重新定义：

1. **初识旋律：** 节奏色块、琴键定位、右手短动机；
2. **右手入门：** 右手旋律、基础识谱与指法；
3. **左手伴奏：** 低音区定位、伴奏型与左手指法；
4. **双手合奏：** 大谱表、同步点与低速合手；
5. **情感表达：** 乐句、力度和基础踏板；
6. **速度提升：** 困难小节循环、稳定性和目标速度；
7. **完整演奏：** 分段串联、完整录制和舞台时刻。

课程采用“快速获得局部成果，逐步完成整首目标版本”的路径。初期通过缩短乐句、分手练习、降低速度、等待模式和辅助提示降低任务难度，但不频繁更换或持续删减目标乐谱；随着能力提升，系统逐步恢复完整音符、双手配合和连续演奏，最终让用户完整弹完选定的带指法初学版。

### 11.2 每日练习结构

建议每次 10–20 分钟，由以下模块组成：

1. 30–60 秒热身；
2. 2–4 个新技能微挑战；
3. 目标曲短乐句练习；
4. 昨日困难小节复习；
5. 一次轻量演奏验收；
6. 明确的进步总结。

### 11.3 30 天目标

“30 天学会弹奏”是产品叙事目标，不应成为对所有用户的硬性承诺。系统应根据练习频率和掌握情况调整日程，并将完成条件定义为能力达标，而不是简单签到满 30 天。

### 11.4 验证期曲目基准

验证期以一份带指法的《梦中的婚礼》初学版乐谱作为课程内容基准。课程拆分、左右手顺序、指法提示、困难小节和目标演奏效果均围绕同一版本设计，避免不同编曲之间的音符、指法和难度差异干扰产品判断。

| 参考层级 | 资料 | 在产品设计中的作用 |
|---|---|---|
| 主要乐谱参考 | 带指法的初学版 PDF | 确定课程范围、音符、指法、左右手拆分和乐段顺序 |
| 主要演奏参考 | 与该乐谱对应的演奏视频 | 理解速度、节奏、乐句、双手配合和完整演奏听感 |
| 辅助数据参考 | MusicXML、ABC 等结构化乐谱 | 辅助校对并研究后续内容数据模型，不作为课程版本的最终依据 |
| 可选节奏参考 | 网络 MIDI 资料 | 在确有需要时辅助分析时序，不构成验证期必要依赖 |

当前选择解决的是产品可行性验证阶段的内容一致性问题，不代表已经确定正式商用编曲或取得公开分发授权。相关资料链接与调研说明见 20.2 节。

这份约 35 小节的初学版既是课程内容基准，也是验证期的完整学习终点。产品简化的是每次练习呈现的信息量和动作要求，而不是另行制作一个不断删减音符的最终版本。接近专业演奏版本的速度、编配和表现要求不纳入本阶段目标，可在未来作为进阶课程扩展。

## 12. 激励系统

### 12.1 应保留的激励

- 连续练习天数；
- 每日小目标；
- 章节星级或熟练度；
- 经验值与等级；
- 首次完成、无中断完成、目标速度完成等成就；
- 从第一小节到完整曲目的可视化距离。

### 12.2 激励原则

- 奖励真实练习行为，而非无意义点击；
- 连胜中断不应产生强烈羞耻或惩罚；
- 失败后强调可恢复的下一步；
- “舞台时刻”应成为完成整曲的情感高潮；
- 用户可以随时重听自己的进步，而不只看到数字。

## 13. 产品信息架构

### 13.1 iPad 导航模型

- 学习地图、曲库、成就和设置使用适合 iPad 的轻量导航；
- 进入练习后切换为沉浸式横屏，不长期占用空间展示侧边导航；
- Chrome Web 原型与后续 iPad 原生应用应保持相同的核心练习信息架构；
- 练习中只保留退出、进度、速度、提示和设备状态等必要控制；
- 课程结束后回到复盘页，再由用户选择继续、重练困难小节或返回学习地图。

### 13.2 学习之旅

核心首页，展示：

- 当前章节与下一课；
- 距离完整弹奏的进度；
- 今日建议练习；
- 最近困难小节；
- 一键继续练习。

### 13.3 练习室

承载动态乐谱、虚拟键盘、设备连接、速度与提示设置，以及所有实时练习模式。

### 13.4 曲库

MVP 以《梦中的婚礼》为唯一完整课程。其他曲目可以展示为未来方向，但不应在核心体验尚未成立前扩张内容范围。

### 13.5 成就

记录与真实演奏里程碑相关的成就和最佳表现。

### 13.6 我的

包括练习偏好、输入设备、提示强度、音量、无障碍选项与账户进度。

## 14. 音乐视觉语言

### 14.1 目标

创建“月光琴房自己的音乐语言”：友好、可读、可动，并能从游戏化提示平滑过渡到真实乐谱。

### 14.2 核心元素

- 圆润、清晰的音符与休止符；
- 彩色节奏块及不同时值变体；
- 与整体视觉一致的升降号、连线和指法数字；
- 高低音谱表与双手标记；
- 正确、接近、错误和已掌握状态；
- 适用于移动和桌面的不同密度版本。

### 14.3 实现方向

可基于符合 SMuFL 规范的音乐字体建立标准记谱能力，再叠加月光琴房自有的字重、圆角、颜色和动态状态。不能仅用普通文本字体近似音乐符号，也不能让装饰风格降低节奏与音高的可读性。

## 15. MVP 范围建议

### 15.1 必须具备

- 一个可完整体验的核心练习流程；
- iPad 横屏沉浸式练习布局；
- iPad 触控虚拟键盘与节奏板；
- 桌面 Chrome 开发、调试和演示能力；
- iPad 横屏视口的确定性适配；
- 彩色节奏块从右向左移动；
- 固定判定线；
- 虚拟钢琴键盘；
- 音高、时机和时值反馈；
- 右手、左手和双手练习模式；
- 大谱表的基础双手练习；
- 指法数字与提示强度切换；
- 困难小节循环；
- 练习结果与本地进度保存；
- 《梦中的婚礼》的一个代表性短乐段课程。

### 15.2 应尽快加入

- Chrome Web MIDI 输入与权限流程；
- 真实 iPad 上的触控、布局与可读性验证；
- 速度调整与学习/跟随/演奏模式；
- 课程地图与每日练习；
- 完整目标曲的分段内容；
- 基础账号与跨设备进度。

### 15.3 暂不纳入

- 大规模曲库；
- iPad 原生工程实现；
- Web 原型的应用商店发布、深度系统集成和长期兼容承诺；
- 麦克风高精度识音；
- AI 摄像头手型评分；
- 原声钢琴麦克风高精度识别；
- 教师后台与社交社区；
- 高级踏板、触键和音乐表现力分析；
- 付费体系的完整设计。

### 15.4 进入 iPad 原生开发的建议门槛

满足以下条件后，再启动完整的 iPad 原生工程：

1. 零基础用户能够在较少人工解释下完成第一节节奏练习；
2. 用户能够理解色块、音符、琴键和指法之间的渐进关系；
3. 右手、左手到双手大谱表的过渡不存在结构性理解障碍；
4. 右向左运动乐谱在 iPad 横屏视口中清晰、可预判且不会引发明显焦虑；
5. 错误反馈能够帮助用户在下一轮练习中改善，而不只是告知失败；
6. 困难小节循环能显著提高后续完成率；
7. 目标用户愿意继续下一课，并认可“最终弹会《梦中的婚礼》”的课程价值；
8. 课程、谱面、事件时间轴和评分规则已经形成独立于 Web UI 的稳定数据模型。

具体通过阈值在首轮用户测试前另行制定，避免先有数字、后找证据。

### 15.5 首轮用户测试分组

首轮测试不假设用户普遍拥有 MIDI 电子琴，并采用两组并行验证：

| 用户群体 | 主要输入方式 | 核心验证目标 |
|---|---|---|
| 无 MIDI 设备用户（主要群体） | 屏幕键盘 | 入门是否简单、节奏色块是否直观、从琴键到识谱的过渡是否成立 |
| MIDI 电子琴用户（辅助群体） | 桌面 Chrome Web MIDI | 真实琴键输入、节奏判定，以及屏幕练习成果能否迁移到电子琴 |

两组用户使用相同的核心课程结构、共享的学习进度和相同的基础通过标准，但成绩按“屏幕完成”与“MIDI 完成”分别标记和分析，避免设备投入度和学习动机差异掩盖真实问题。

Web MIDI 是首轮测试的可选增强能力，不是注册、开始课程或完成核心学习路径的必要条件。核心课程必须能够通过屏幕键盘独立完成。

## 16. 成功指标

### 16.1 核心体验指标

- 首次用户完成第一项练习的比例；
- 首次成功发声所需时间；
- 第一节课完成率；
- 困难小节重练后的改善率；
- 从单手进入双手练习的转化率；
- 用户完成第一个完整乐段的比例。

### 16.2 留存指标

- 次日、7 日和 30 日练习留存；
- 每周有效练习天数；
- 每次有效练习时长；
- 中断后恢复练习的比例。

### 16.3 最终结果指标

- 完成目标曲所有章节的比例；
- 在不显示琴键字母的情况下完成乐段的比例；
- 在大谱表模式完成双手乐段的比例；
- 达到“完整弹会”标准的用户比例；
- 达到“熟练演奏”和“舞台时刻”标准的用户比例；
- 各演奏维度中最常见的未达标项及其改善率。

> 指标中的“完成”必须包含真实技能门槛，不能只以打开页面、播放示范或签到作为完成。

## 17. 风险与验证计划

| 风险 | 可能后果 | 优先验证方式 |
|---|---|---|
| 信息过多，练习页仍然复杂 | 新手不知道看哪里 | 观察首次练习，记录视线和首次成功时间 |
| 色块到音符的过渡太突然 | 用户会玩节奏但不会识谱 | 测试渐变揭示与直接切换两种方案 |
| 双手大谱表在不同尺寸 iPad 上密度不合适 | 乐谱难读或虚拟琴键过窄 | 以横屏为基准验证紧凑与宽屏两档布局 |
| 手掌遮挡屏幕下半区或造成误触 | 屏幕键盘练习挫败 | 在真机测试双手触控、谱架和桌面三种姿态 |
| 桌面 Chrome 原型与真实 iPad 使用姿态存在差异 | Web 验证结论无法迁移到最终产品 | 固定使用 iPad 横屏视口，并定期在真实 iPad 上验证布局与触控 |
| Chrome Web MIDI 让团队误以为 iPad Web 同样可用 | 错误估计原生开发成本 | 将 Web MIDI 明确标为桌面验证工具，原生输入能力单独立项 |
| Web Audio 或浏览器调度出现延迟 | 节拍和实时反馈失去可信度 | 建立输入到判定再到声音反馈的端到端延迟测试 |
| 指法提示造成视觉拥挤 | 读谱速度下降 | 测试全部显示、变化时显示和手型条三种方案 |
| 虚拟键盘体验好但不能迁移到真琴 | 游戏成绩与演奏能力脱节 | 使用桌面 Chrome Web MIDI 与真实电子琴验证技能迁移效果 |
| 30 天承诺带来压力或不可信 | 用户失望、流失 | 用自适应计划替代固定日历式承诺 |
| 游戏化目标挤压真实练习 | 用户追分但不会弹 | 将经验值与技能掌握和真实演奏绑定 |
| 验证期参考资料被误当作已获授权的商用内容 | 公开发布时产生版权与版本风险 | 验证期仅用于内部课程研究；进入公开发布或商业化准备阶段后重新确认编曲与授权 |

- 第一阶段采用桌面 Chrome Web 应用验证核心功能；
- Web 原型界面优先适配 iPad 横屏尺寸和触控交互；
- 核心功能验证通过后，开始开发正式 iPad 原生应用；
- 以最终完整弹奏《梦中的婚礼》为目标；
- 借鉴 Duolingo Music 的低门槛、短挑战和乐谱—键盘一体交互；
- 最基础练习只显示彩色节奏矩形，不显示传统音符；
- 乐谱从右向左移动；
- 需要覆盖左右手合奏与大谱表练习；
- 需要面向新手的指法和指尖/手型提示；
- 需要形成月光琴房自己的音乐视觉语言；
- 不假设首批用户普遍拥有 MIDI 电子琴；
- Web MIDI 作为首轮测试的可选增强能力，不作为开始或完成课程的必要条件；
- 首轮测试同时包含无 MIDI 用户和 MIDI 用户，分别验证教学易用性与真实琴键迁移。
- 验证期以带指法的《梦中的婚礼》初学版 PDF 为课程基准，并以其对应演奏视频作为速度、节奏和乐句参考；正式商用版本与授权延后至核心产品可行性得到验证后处理。
- 课程以“快速获得局部成果，逐步完整弹完选定的初学版”为目标；练习过程可以降速、分手和减少信息，但不以持续删减最终乐谱作为主要教学方式。
- 教学顺序先从第 6–35 小节较稳定的主体进入，再学习第 1–5 小节引子；最终演奏仍按原曲顺序从引子开始。
- 验证期完整演奏只演奏第 1–35 小节一遍，不执行参考谱中的反复记号。
- 课程主线关卡全部必修，不根据用户表现自动跳关；用户表现只影响尝试次数、提示强度和是否增加补救练习。
- 指法引导以琴键高亮和指法数字为主要实时提示，手型示意用于手位变化，短视频仅用于用户主动查看的难点动作示范。
- 乐谱运动规则由练习目标决定：学习新音与指法时可以完全等待，节奏和跟随练习保持低速连续，演奏验收不中断。
- 音名默认使用 `C / D / E`，允许用户切换为 `do / re / mi`；入门阶段可短暂双标，熟练后只保留用户选择的一套并逐步淡出。
- 完整演奏使用多维硬性门槛，分为“完整弹会、熟练演奏、舞台时刻”三级；验证期的完整弹会初始标准为整曲双手不中断、音符正确率不低于 90%、节奏达标率不低于 80%、速度不低于参考速度的 70%。
- 屏幕键盘与 MIDI 键盘共享课程路径、解锁进度和基础通过标准；所有验收均可用屏幕键盘完成，成绩按输入方式分别标记，MIDI 力度与踏板数据不影响验证期解锁。

### 18.2 当前建议

- 采用固定判定线；
- 使用分层提示与逐步淡出机制；
- Web MVP 确定支持屏幕键盘，并为部分测试用户提供桌面 Chrome Web MIDI；
- 使用“右手 → 左手 → 双手”的乐段进阶；
- 把困难小节循环作为核心纠错机制；
- 先做好一首歌、一个完整核心流程，再扩曲库。

### 18.3 延后决策事项

- 启动 iPad 原生开发所需的用户测试样本量和量化通过阈值。该问题不影响当前课程与核心交互设计，待 Web 验证范围和测试方案更明确后再讨论。

## 19. 下一阶段建议产物

在进入完整开发前，建议围绕同一个 60–90 秒代表性乐段，先完成以下产品验证：

1. 纯节奏色块练习；
2. 色块加入音名与琴键定位；
3. 音符渐显与指法提示；
4. 右手、左手分练；
5. 双手大谱表低速合奏；
6. 练习结果与困难小节重练。

这个纵向切片能够验证月光琴房最重要的产品假设：**用户能否在不被乐理压垮的情况下，从节奏游戏自然过渡到真实双手钢琴演奏。**

具体工程架构、实施阶段与验收标准见配套文档《月光琴房产品实现规划 v0.1》。

## 20. 参考依据

### 20.1 平台技术依据

- Chrome 官方说明，Web MIDI API 可以让网站连接 MIDI 键盘或控制器；Chrome 中调用该能力需要用户明确授权：[Access to MIDI devices now requires user permission](https://developer.chrome.com/blog/web-midi-permission-prompt)。
- WebKit 的 Web MIDI API 主跟踪项当前仍为 `NEW`。因此桌面 Chrome Web MIDI 仅用于原型验证，不能推导出 iPad 浏览器具备相同能力：[Web MIDI API — WebKit Bug 107250](https://bugs.webkit.org/show_bug.cgi?id=107250)。

### 20.2 验证期课程内容参考

- **主要乐谱参考：** [Mariage D'Amour Piano Easy（With finger numbers）PDF](https://truongca.com/images/sheet/pdf/marriage/marriage-d-amour-piano-paul-de-senneville-truongca.com.pdf)。该版本带有面向初学者的指法标注，是验证期课程范围、乐段结构和指法设计的基准。
- **主要演奏参考：** [YouTube：对应演奏视频](https://www.youtube.com/watch?v=DTrYGqIxT3Y)。用于理解上述乐谱对应的节奏、速度、乐句、双手配合及完整演奏效果，不直接提取视频音频作为产品素材。
- **MusicXML 辅助资料：** [Sao Mai Center 乐谱页面](https://saomaicenter.org/en/music-library/paul-de-senneville-mariage-damour)及其 [MXL 文件](https://saomaicenter.org/sites/default/files/music_sheets/2020-08/Paul_de_Senneville_-_Mariage_dAmour.mxl)。文件已确认可解析，包含一个钢琴声部和 83 小节，可用于结构化数据研究与交叉校对。
- **现有 ABC 辅助资料：** 早期原型中的《梦中的婚礼》ABC 转录文件。该文件包含左右手声部和多个拍号变化，可作为后续内容数据模型的研究输入；它不随本仓库发布，也不作为最终校准依据。
- **MIDI 调研资料：** [MidiShow：39 秒《Mariage D'Amour》片段](https://www.midishow.com/en/midi/mariage-d-amour-midi-download-212211)。页面标注该片段为 39 秒、120 BPM，并包含延音踏板事件，但下载需要账户积分，因此不作为验证期必要依赖。
