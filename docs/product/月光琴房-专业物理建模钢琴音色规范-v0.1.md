# 月光琴房专业物理建模钢琴音色规范

> 版本：v0.1  
> 状态：Proposed / 设计基线，尚未实现  
> 更新日期：2026-09-06  
> 适用范围：Web、iOS、Android、macOS、Windows、Linux  
> 质量目标：Pianoteq 级 professional 虚拟钢琴的可演奏性、声学可信度、制作能力与实时性能

---

## 0. 文档目的

本文定义月光琴房专业钢琴音色系统的最终产品级约束。它不是临时原型方案，也不把实现拆成一套以后必然推翻的“简化引擎”和“正式引擎”。所有正式实现必须从一开始服从本文的物理模型、Rust 内核、跨平台、实时性能、可验证性与知识产权边界。

本文所说的 **Pianoteq 级** 是质量和用户体验基准，不是复制 Pianoteq 的源代码、模型参数、预设、专利实现或产品界面。月光琴房必须形成独立设计、独立代码、独立模型包和可审计的数据来源。

规范中的关键词含义如下：

- **必须（MUST）**：违反即不能作为专业钢琴引擎发布；
- **禁止（MUST NOT）**：任何实现不得采用；
- **应该（SHOULD）**：除非有测量证据和架构决策记录，否则必须采用；
- **可以（MAY）**：允许的实现选择，不构成发布门槛。

## 1. 核心产品定义

月光琴房要构建的不是三个经过不同 EQ 处理的合成音色，也不是一个触发钢琴录音切片的采样器，而是：

> 一套由实时数学模型生成声音的专业虚拟钢琴系统。演奏者控制的是具有琴键机构、非线性琴槌、200 余根持久琴弦、琴桥、音板、制音器、踏板、交感共鸣、琴体辐射和虚拟麦克风的完整乐器状态。

产品由两个长期稳定的层组成：

1. **Moonlight Physical Piano Engine**：统一的 Rust 实时物理建模与 DSP 内核；
2. **Moonlight Instrument Model Packs**：独立校准的乐器定义、物理参数、降阶模型和空间辐射数据。

所有平台使用同一套物理方程、事件语义、模型包格式、参考渲染场景和质量验收标准。

## 2. 从专业演奏者评价提炼出的质量支柱

Modartt 公布的钢琴家、作曲家、现场乐手和制作人评价表明，professional 物理建模钢琴的价值不只在“单个音像不像录音”，而在以下能力同时成立。

### 2.1 演奏者与声音直接连接

必须让演奏者感觉声音由自己的触键、释放、踏板和演奏历史连续产生，而不是触发一段固定素材。系统必须对极弱奏、极强奏、重复音、连奏、断奏、半踏板和快速换踏保持即时且可预测的响应。

### 2.2 完整且连续的动态范围

力度变化必须同时改变：

- 琴槌接触时间和力峰值；
- 起音速度与噪声；
- 泛音能量分布；
- 频谱重心；
- 各模态衰减；
- 琴桥与音板激励；
- 整体响度。

禁止使用“固定波形乘 Gain”模拟力度，禁止出现可听的 velocity layer 切换或动态空档。

### 2.3 踏板、制音器和共鸣属于同一机械系统

延音踏板必须改变全部制音器和开放琴弦的状态。半踏板、重新踩踏、flutter pedal、踏板捕获、sostenuto 和 una corda 必须是连续、可组合且有历史状态的行为。交感共鸣不能实现成额外混响。

### 2.4 每架乐器有独立身份

三角钢琴、温暖录音室钢琴和立式钢琴必须来自不同的结构或完整 voicing 参数，而不能只是改变截止频率、混响和失谐宽度。

### 2.5 裸音、舞台和混音都成立

输出必须支持独奏、教学、现场和录音制作。专业质量包括低延迟、稳定性、空间辐射、虚拟麦克风、响度一致性、单声道兼容性和进入混音后的存在感。

### 2.6 深度编辑仍然保持物理可解释

琴槌硬度、弦长、unison width、音板阻抗、调律、琴况、制音器、琴盖和麦克风位置等参数必须对应连贯的声学变化，而不是互不相关的效果器旋钮。

### 2.7 小体积、快速加载和低 CPU 是音色品质的一部分

专业演奏需要稳定的实时期限。平均 CPU 较低但偶发爆音，或桌面可用但手机热降频后失效，都不符合本规范。

## 3. 目标与非目标

### 3.1 必须达到的目标

- 全 88 键物理建模；
- 连续力度、释放速度与高分辨率踏板；
- 持久琴弦、琴桥和音板状态；
- 双向琴弦—琴桥—音板耦合；
- 全局交感共鸣；
- 三弦组拍频、刚性不谐和度和音区连续变化；
- 低音横向、纵向及必要的非线性耦合；
- 连续制音器接触与完整踏板行为；
- 独立的琴体声辐射、虚拟麦克风与房间效果；
- 从开始即使用 Rust 实现正式 DSP；
- Web 使用 Rust/WASM + AudioWorklet；
- 手机和桌面使用同一 Rust 核心的原生构建；
- 在专业演奏、制作、跨平台和长时间热稳态测试中通过发布门槛。

### 3.2 明确的非目标

- 不复制某一商业钢琴型号的商标化数字孪生；
- 不声称拥有项目未实际测量的内部结构尺寸；
- 不依赖项目所有者提供实体钢琴或现场录音；
- 不在运行时播放逐音钢琴采样；
- 不以 Tone.js、Salamander 或其他采样器作为正式发声内核；
- 不逆向提取 Pianoteq 或其他商业产品的模型、参数和音频资产；
- 不把一套合成算法的三组滤波参数包装成三架钢琴；
- 不把房间混响、EQ、压缩或立体声扩展误称为物理钢琴模型。

### 3.3 允许的数据形式

正式乐器核心运行时可以包含：

- 物理参数；
- 极点、留数、状态空间矩阵和降阶系数；
- 参数映射曲面；
- 辐射滤波器和系统辨识系数；
- 不包含可识别演奏内容的短系统响应或残差滤波数据；
- 经过许可且与钢琴核心分离的房间脉冲响应。

正式乐器核心禁止包含：

- 逐音、逐力度或逐奏法的音频波形；
- release、pedal 或 resonance 的触发式录音素材；
- 从商业产品中提取的预设、模型系数或音频。

## 4. 总体系统架构

```text
公开授权的数据、论文与物理合理范围
                 │
                 ▼
      Offline Instrument Compiler
  高精度结构模型 / 参数辨识 / 感知优化
  保稳定与保被动的模型降阶 / 空间拟合
                 │
                 ▼
      Moonlight Instrument Model Pack
                 │
        ┌────────┴────────┐
        │                 │
        ▼                 ▼
 Web Audio Host       Native Audio Hosts
 AudioWorklet         Core Audio / AAudio
 Rust → WASM          WASAPI / PipeWire
        │                 │
        └────────┬────────┘
                 ▼
       Moonlight Rust DSP Core
 琴键机构 / 琴槌 / 琴弦 / 琴桥 / 音板
 制音器 / 踏板 / 交感共鸣 / 空间辐射
                 │
                 ▼
        Stereo / Binaural / Multichannel
```

### 4.1 离线计算与实时计算必须分离

高成本有限元、边界声学、参数扫描、优化和模型降阶属于离线 Instrument Compiler。实时线程只运行经过验证的降阶物理模型。

“做到最好”不等于在音频回调中暴力求解完整有限元网格，而是：

> 离线模型足够深入，实时模型在明确的声学、数值和感知误差约束下足够准确、稳定和高效。

### 4.2 一套 Rust 内核，多种宿主

- **Web**：Rust 编译为 WASM，在 `AudioWorkletProcessor` 的音频渲染线程中执行；
- **iOS / macOS**：Rust 编译为原生静态库，由 Core Audio / Audio Unit 回调调用；
- **Android**：Rust 编译为原生 `.so`，由 AAudio / Oboe 数据回调调用；
- **Windows**：Rust 原生库接入 WASAPI；
- **Linux**：Rust 原生库接入 PipeWire，必要时兼容 ALSA；
- **离线渲染和测试**：直接调用同一 Rust DSP 核心。

原则为：

> Rust everywhere，WASM on Web。

WASM 不是 Rust 的替代品，AudioWorklet 也不是以后会被 WASM 替换的临时引擎。AudioWorklet 是 Web 端的实时音频宿主，WASM 是其中运行的 Rust DSP 产物。

### 4.3 UI 与音频线程边界

UI 可以采用 Web 技术、Tauri 或平台原生界面，但：

- PCM 数据禁止经过 WebView IPC；
- JavaScript、Swift、Kotlin 或 UI 线程禁止逐采样驱动 DSP；
- UI 只发送带时间戳的控制和演奏事件；
- 模型加载、参数编译和文件 I/O 在非实时线程完成；
- 实时线程只读取已经验证并预分配的数据。

## 5. 输入、时间与演奏事件

### 5.1 音频时钟是唯一时间基准

乐谱、MIDI、屏幕键盘、动画和音频必须映射到同一高精度时间轴。事件在进入 DSP 前转换为目标音频块内的 sample offset。

```rust
pub enum PianoEvent {
    NoteOn {
        note: u8,
        velocity: f32,
        sample_offset: u32,
    },
    NoteOff {
        note: u8,
        release_velocity: f32,
        sample_offset: u32,
    },
    Sustain {
        position: f32,
        sample_offset: u32,
    },
    Sostenuto {
        position: f32,
        sample_offset: u32,
    },
    UnaCorda {
        position: f32,
        sample_offset: u32,
    },
    Parameter {
        id: ParameterId,
        value: f32,
        sample_offset: u32,
    },
}
```

### 5.2 控制器校准

系统必须支持：

- MIDI 1.0 velocity；
- release velocity；
- CC64、CC66、CC67；
- 高分辨率踏板输入；
- MIDI 2.0 / per-note controller 的可扩展映射；
- 不同键盘的 velocity curve 校准；
- 输入抖动、时间戳和 USB/Bluetooth 路径诊断。

控制器校准不得改变物理模型，只负责把设备输入映射为标准化的琴键、琴槌和踏板控制量。

## 6. 琴键机构与非线性琴槌

### 6.1 机构状态

每个键必须具有可持续的机械状态，至少覆盖：

- 琴键位移和速度；
- 杠杆比；
- 联动器、顶杆、擒纵与复震行为；
- 琴槌位置、速度和质量；
- 回弹；
- 快速重复音时尚未完全复位的状态；
- una corda 对击弦位置和击弦数量的影响。

MIDI 输入可以省略不可观测的中间运动轨迹，但从输入到琴槌初速度的映射必须连续、可校准，并保留重复击键所需的状态。

### 6.2 琴槌—琴弦接触

禁止用固定 thump、白噪声 click 或简单包络替代琴槌接触。核心接触模型至少应表达 felt 的非线性压缩、滞后与能量损耗。定义压缩量：

\[
\delta(t)=x_h(t)-y_s(t)
\]

先计算候选压缩接触力：

\[
F_h^*(t)=K[\delta(t)]_+^p + C[\delta(t)]_+^q\dot{\delta}(t)
\]

完整接触力必须采用单向、非黏附约束：

\[
F_h(t)=
\begin{cases}
\max\left(0,F_h^*(t)\right), & \delta(t)>0 \\
0, & \delta(t)\le 0
\end{cases}
\]

\[
m_h\ddot{x}_h=-F_h
\]

其中 `K > 0`、`C ≥ 0`、`p > 1`、`q ≥ 0`。`F_h` 表示完整的压缩接触力，任何加载或卸载阶段都禁止为负。卸载期间一旦候选力降至零，接触必须结束；在重新产生正压缩和闭合速度之前不得恢复接触，因此模型不能产生拉伸、黏附或把琴槌重新吸向琴弦的力。

离散求解器必须同时证明：

- 完整接触力始终非负；
- felt 阻尼在闭合接触循环中不增加系统净机械能；
- 接触分离和重新接触不产生数值脉冲或额外能量；
- 过采样、隐式求解或其他稳定化策略不会改变上述单向接触语义。

模型必须支持：

- 不同音区的琴槌质量；
- felt 硬度、非线性指数与损耗；
- 压缩和回弹的滞后；
- 击弦点与接触宽度；
- 弱奏到强奏连续变化；
- 重复音受残余弦振动和机构状态影响；
- 接触阶段的稳定过采样或等效高精度求解。

所有非线性求解器必须证明有界、稳定，并通过单向接触、能量和极端输入测试。

## 7. 琴弦系统

### 7.1 全键盘与真实弦组结构

系统必须覆盖 88 键和完整弦组：

- 低音单弦或双弦；
- 中高音三弦；
- 音区间连续变化的弦长、线密度、张力、刚度和缠弦特性；
- 每根弦独立的失谐、阻尼和耦合；
- 琴枕端、琴桥端和 duplex scale 的边界行为。

### 7.2 持久状态

每根弦都必须是持久动态系统，而不是按键时创建、松键时销毁的固定 voice。静止琴弦可以进入可逆休眠，但其状态推进必须可解析恢复，不能丢失交感共鸣和再击弦历史。

### 7.3 刚性与不谐和度

必须表达弦刚性导致的非整数倍 partial：

\[
f_n \approx n f_0\sqrt{1 + Bn^2}
\]

其中 `B` 必须随音高、弦设计、缠弦和实际校准连续变化，不能只用三个音区常量。

### 7.4 多方向与纵向振动

模型应至少包含：

- 两个横向极化方向；
- 极化之间的轻微频率和阻尼差异；
- 与琴桥方向相关的耦合；
- 低音区纵向振动；
- 必要的横向—纵向非线性耦合；
- 低音 phantom partial 和金属感的可验证来源。

### 7.5 三弦组

三弦区必须为每根弦保存独立状态。unison width 不只是三个固定 oscillator 的 detune，而是独立琴弦在失谐、衰减、耦合、相位和琴桥负载下自然形成的拍频。

## 8. 琴桥、音板与琴体

### 8.1 全局共享系统

音板是整架钢琴共享的动态系统，不是每个音符后面的卷积混响。琴弦通过不同琴桥位置向音板输入能量，音板也通过琴桥反向影响开放琴弦。

\[
\mathbf{M}\ddot{\mathbf{x}} +
\mathbf{C}\dot{\mathbf{x}} +
\mathbf{K}\mathbf{x}
=
\mathbf{B}\mathbf{f}_{bridge}
\]

### 8.2 离线高阶模型与保结构降阶

离线模型可以使用有限元、模态分析、边界元或混合结构声学方法，覆盖：

- 音板各向异性；
- 肋木；
- 琴桥；
- 边框和连接边界；
- 琴盖或立式琴背板；
- 空气负载；
- 不同输入和听音位置。

实时端必须使用保稳定、保因果、优先保被动性的降阶状态空间模型：

\[
\mathbf{z}_{k+1}=\mathbf{A}\mathbf{z}_k+\mathbf{B}_r\mathbf{f}_k
\]

\[
\mathbf{y}_k=\mathbf{C}_r\mathbf{z}_k
\]

### 8.3 禁止预设固定模态数

不得先规定“32、64 或 128 个音板模态”再适配模型。最终阶数必须由以下误差共同决定：

- 琴桥机械导纳；
- 模态频率和阻尼；
- 多输入、多输出传递函数；
- 空间辐射；
- 弦—板能量交换；
- 听觉可辨识误差；
- 实时性能合同。

可辨识的中低频使用显式空间模态；高频密集区域可使用统计模态簇、参数化极点—留数模型或其他经过验证的多分辨率表示，但禁止简单替换成白噪声或普通混响。

## 9. 交感共鸣、制音器与踏板

### 9.1 双向交感共鸣

系统必须实现：

```text
琴槌 ↔ 琴弦 ↔ 琴桥 ↔ 音板 ↔ 其他开放琴弦
```

开放琴弦依据自身模态和当前音板状态吸收能量。按住但未击打的键、延音踏板抬起的制音器和 sostenuto 捕获的琴弦必须产生符合状态的响应。

交感共鸣禁止通过“检测和弦后播放额外声音”或增加 reverb send 实现。

### 9.2 连续制音器

制音器必须表示为频率相关、连续变化的接触阻抗，而不是布尔开关：

\[
Z_d(\omega,q)=R_d(\omega,q)+jX_d(\omega,q)
\]

其中 `q` 为接触深度。模型必须表达高频先被毛毡吸收、低频衰减稍慢以及接触速度造成的瞬态差异。

### 9.3 踏板行为

必须支持：

- 连续延音踏板；
- 半踏板；
- repedal；
- flutter pedal；
- 踏板捕获；
- sostenuto；
- una corda；
- key-up 与 pedal-up 的不同阻尼轨迹；
- 与动作速度相关的制音器和踏板机械声；
- 踏板变化时现有弦状态不被重置。

机械噪声可以由物理或参数化噪声模型生成，但不得依赖触发式录音素材。

## 10. 声辐射、虚拟麦克风与房间

### 10.1 琴体辐射

音板位移不能直接作为最终 PCM。模型必须把音板表面速度、空气负载、频率相关辐射效率、琴盖或柜体遮挡、传播距离和方向性映射为声压。

\[
p_k(t)=\sum_m r_{k,m}(\mathbf{x}_k,\mathbf{d}_k)
          s_m(t-\tau_{k,m})
\]

### 10.2 虚拟麦克风

必须支持至少：

- 演奏者视角；
- 琴内近距；
- 经典立体声对；
- 观众或房间视角；
- binaural virtual head；
- 可扩展的多声道输出。

移动麦克风后，必须真实改变频谱、相位、到达时间、立体声相关性和遮挡，而不只是 pan 与音量。

### 10.3 乐器与房间严格分离

信号链必须清晰区分：

```text
物理乐器 → 琴体辐射 → 虚拟麦克风 → 房间 / 制作效果
```

房间混响、EQ、压缩、限制器和其他制作效果不得掩盖核心乐器模型缺陷。质量评测必须同时包含完全干声与制作预设。

---

## 11. 乐器模型与初始产品目录

### 11.1 模型层级

系统必须区分：

- **Instrument**：琴弦设计、机构、琴桥、音板、琴体和辐射；
- **Voicing**：琴槌 felt、unison、调律、琴况和阻尼；
- **Capture**：琴盖、麦克风和空间；
- **Mix preset**：EQ、动态与房间效果。

四个层级必须能够独立寻址和任意组合。切换 Instrument、Voicing、Capture 或 Mix preset 中的任意一层，禁止隐式修改其他层；组合不兼容时必须在加载前显式拒绝，而不能静默替换用户的选择。

禁止用 Capture 或 Mix preset 冒充另一架 Instrument。

### 11.2 Moonlight Concert Grand

完整独立的三角钢琴模型，至少具有：

- 长弦列和独立音区设计；
- 三弦组与 stretch tuning；
- 大型音板和琴盖；
- 宽广空间辐射；
- 适合古典独奏、教学和制作的连续动态；
- 专业演奏者可直接使用的 Neutral voicing。

### 11.3 Moonlight Studio Warm Grand

Studio Warm 可以与 Concert Grand 共享经过证明相同的结构几何，但必须是完整校准的 voicing，而非后级低通。它至少同时改变：

- felt 硬度与接触时间；
- 力度—频谱映射；
- unison width；
- partial 衰减；
- 音板损耗；
- 调律和逐音散布。

选择 Studio Warm 禁止隐式选择或修改 Capture、Room 或 Mix preset。它必须与 Concert Grand 的所有兼容 Capture 任意组合，以便在相同麦克风和房间下进行受控 A/B 比较。

### 11.4 Moonlight Bright Upright

必须是一架独立立式钢琴模型，至少具有：

- 更短且不同分区的弦列；
- 独立 bass winding 与不谐和度曲线；
- 不同的击弦机构和击弦点；
- 竖直音板、背板、柜体和墙面耦合；
- 独立琴桥位置和空间辐射；
- 更窄但真实的声场；
- 独立机械噪声、阻尼和调律特征。

## 12. Offline Instrument Compiler 与数据策略

### 12.1 不要求项目所有者提供真实钢琴

项目必须能够依靠公开授权资料、独立购买或委托获得的数据、声学研究和物理合理范围完成校准。不得把“用户提供一台真实钢琴”作为产品成立条件。

### 12.2 数据用途

外部录音只允许用于：

- partial 频率和不谐和度估计；
- 各 partial 衰减曲线；
- 琴槌力度与起音频谱关系；
- 三弦拍频；
- release、pedal 和 resonance 行为分析；
- 多麦克风空间辐射拟合；
- 独立盲听和回归验证。

运行时不得播放这些录音。

### 12.3 校准集、开发验证集与密封外层测试集

数据角色必须在任何参数拟合或主观调校前登记并严格分离：

- **校准集**：允许用于参数拟合、模型选择和优化；
- **开发验证集**：允许反复查看，用于工程迭代、误差分析和阈值调试；
- **跨钢琴泛化集**：用于验证是否只拟合了单一钢琴或录音条件；
- **不可变外层测试集**：用于最终发布泛化证据，数据、标签、结果和逐样本误差在候选冻结前对开发者及调校 agent 保持不可见；
- **专业演奏者盲听集**：其任务、随机化和原始回答必须冻结；一旦结果用于调校，该批结果即转为开发证据，不能继续充当最终独立结论。

一旦任何保留样本的结果、标签、逐样本误差或可定位失败模式被开发者或调校 agent 查看，该样本就永久失去“最终不可见”资格。对同一语料重新切分、换随机种子或移动文件，不能恢复统计独立性。

最终外层测试必须满足：

- 在候选冻结前提交数据清单或承诺哈希、指标、阈值、统计方法和失败规则；
- 由访问受控的流程或独立保管方执行，开发过程不能查询逐样本结果；
- 对一个冻结候选只执行一次正式放行判定；
- 如果测试失败后恢复调校，下一个发布候选必须使用尚未检查的预先密封分区，或新收集且从未被查看的数据；
- 原始结果和访问审计不可变保存，禁止通过删除失败运行重新获得“首次测试”状态。

### 12.4 数据许可与来源清单

每个模型包必须附带 machine-readable provenance manifest，记录：

- 数据来源；
- 许可证；
- 下载日期和校验和；
- 允许用途；
- 处理步骤；
- 是否进入产品参数拟合；
- 是否仅用于研究验证。

可研究的公开参考包括 Salamander Grand、bitKlavier Grand 等，但许可证必须在使用前重新核验。带非商业或相同方式共享限制的数据不得成为商业发布的必要训练或拟合依赖，除非完成法律许可。

### 12.5 参数辨识

Compiler 至少需要：

- 多分辨率频谱分析；
- partial tracking；
- attack / sustain / release 分段；
- 非线性琴槌参数拟合；
- 三弦与拍频估计；
- 多点传递函数与辐射拟合；
- 物理范围约束；
- 稳定性、被动性与因果性约束；
- 感知加权损失；
- 可重现的优化配置和随机种子。

无法从录音唯一反推的内部参数必须被标记为“受物理范围约束的等效参数”，禁止伪称实测值。

## 13. Instrument Model Pack 规范

模型包不是音频库，而是可验证的物理乐器描述。至少包含：

- 格式 magic、schema version 和 engine ABI version；
- instrument、voicing 和 capture 标识；
- 88 键与全部琴弦拓扑；
- 机构与琴槌参数；
- 琴弦模态、阻尼、不谐和度和耦合；
- 琴桥输入映射；
- 音板降阶状态空间；
- 制音器和踏板参数；
- 交感共鸣耦合；
- 空间辐射和虚拟麦克风数据；
- 参数有效范围和插值规则；
- provenance、许可证、生成器版本和校验和；
- 用于自动验证的摘要指标。

模型加载器必须：

- 在进入实时线程前完成完整校验；
- 拒绝 NaN、Inf、不稳定极点、越界索引和不兼容 ABI；
- 对外部模型包进行大小、复杂度和资源上限检查；
- 验证签名或完整性校验；
- 失败时保持现有乐器继续安全发声，不在实时线程 panic。

## 14. Rust DSP 内核规范

### 14.1 crate 边界

建议长期结构：

```text
crates/
├── moonlight-physics/   # 物理方程与参数定义
├── moonlight-dsp/       # 实时渲染、状态、SIMD、事件
├── moonlight-model/     # 模型包 schema、验证和版本
├── moonlight-offline/   # 分析、拟合、参考渲染
├── moonlight-wasm/      # WebAssembly 导出
├── moonlight-ffi/       # 原生平台稳定 C ABI
└── moonlight-bench/     # 声学与性能压力场景

hosts/
├── web-audio-worklet/
├── apple-audio-unit/
├── android-oboe/
├── windows-wasapi/
└── linux-audio/
```

实际目录可以调整，但实时 DSP、离线工具、模型格式和平台宿主必须保持清晰边界。

### 14.2 实时 API

核心接口必须接受任意合理 block size，禁止硬编码 Web Audio 常见的 128 帧：

```rust
pub fn process_block(
    &mut self,
    events: &[PianoEvent],
    outputs: &mut [&mut [f32]],
) -> ProcessReport;
```

要求：

- 事件按 sample offset 有序应用；
- 每个 block 只有有界工作量；
- 输出通道数由配置声明；
- 不依赖平台线程、文件、网络或异步运行时；
- 初始化和模型切换在非实时路径完成；
- 实时路径错误必须转换为静音保护或稳定降级，不得 unwind。

### 14.3 `no_std` 与内存

实时 DSP crate 应保持 `no_std` compatible，或至少在编译和测试层证明渲染路径不依赖 `std` 功能。初始化阶段允许预分配；音频开始后禁止分配和释放。

### 14.4 数值实现

必须同时维护：

- 高精度标量参考渲染器，用于物理和数值正确性；
- 优化的实时标量实现；
- WASM `simd128`；
- ARM NEON；
- x86 SSE/AVX2 或平台等效实现。

数据布局优先使用 Structure of Arrays，以便批量更新模态和耦合状态。跨平台不要求逐 bit 一致，但必须满足频率、衰减、能量、空间和感知误差容差。

### 14.5 时变参数

所有可自动化参数必须：

- 有明确物理单位或归一化语义；
- 在参数域内保持稳定；
- 采用无 zipper noise 的平滑；
- 对已经振动的状态进行合理映射；
- 不通过清空琴弦或音板状态实现变化。

结构不变的参数修改应保留状态。需要切换不同拓扑的完整乐器时，可以使用预加载的双引擎状态和等响度 crossfade，但不得阻塞或中断音频。

## 15. Web、移动与桌面宿主

### 15.1 Web

Web 端必须：

- 在 `AudioWorkletGlobalScope` 内实例化 WASM DSP；
- 每个 render quantum 只进行一次或极少数 block 级 JS/WASM 调用；
- 禁止逐采样跨越 JS/WASM 边界；
- 禁止在 `process()` 中解析 JSON、加载模型或创建数组；
- 提前传递带音频时间戳的事件；
- 在用户手势中正确启动 AudioContext；
- 支持没有 `SharedArrayBuffer` 时的有界消息队列，并把 SAB 作为可选低开销路径；
- 诊断浏览器采样率、block size、输出延迟和 underrun。

### 15.2 Apple 平台

Core Audio / Audio Unit render callback 直接调用 Rust。Swift 或 Objective-C 负责会话、设备路由、UI 和事件入队，禁止进入逐块 DSP 热路径。

### 15.3 Android

AAudio / Oboe data callback 直接调用 Rust。必须请求设备自然采样率和低延迟路径，并记录 frames-per-burst、xrun 和热降频行为。

### 15.4 桌面

桌面端可以使用 Tauri 或其他 UI 外壳，但实时 PCM 始终在原生音频回调内生成。插件格式（如 AU/VST3/CLAP）可以在不分叉核心 DSP 的前提下扩展。

## 16. 实时性能合同

### 16.1 Deadline ratio

定义：

\[
R=\frac{\text{DSP block render time}}
        {\text{audio block duration}}
\]

在每个发布参考设备、48 kHz 和设备常用最小稳定 buffer 下：

- `p50 R ≤ 0.25`；
- `p99 R ≤ 0.45`；
- `p99.99 R ≤ 0.70`；
- 30 分钟热稳态压力测试中不得出现 `R ≥ 1.0` 的 deadline miss；
- 不得出现可归因于引擎的 xrun、underrun、爆音或持续掉帧。

更高采样率和更小 buffer 必须在设备能力检测后启用，并公开实际延迟与负载。

### 16.2 实时线程硬约束

音频启动后：

```text
heap allocation / free      = 0
mutex / blocking lock       = 0
file or network I/O         = 0
logging                     = 0
thread creation             = 0
unbounded loop              = 0
panic / unwind              = 0
model parsing               = 0
```

### 16.3 必测压力场景

- 88 键近同时 note-on；
- 全延音踏板、全部开放琴弦参与共鸣；
- 低音密集重复音与纵向耦合；
- 高频密集 trill；
- 连续快速半踏板与 repedal；
- 最大空间输出和虚拟麦克风数量；
- 44.1、48 和支持设备上的 96 kHz；
- 64、128、256、512 帧 block；
- 前台、后台恢复和设备切换；
- 手机至少 30 分钟热稳态；
- Web 主线程高负载时的音频隔离。

### 16.4 自适应计算边界

允许同一物理模型使用经过验证的自适应求解：

- 低能量模态休眠并解析推进；
- 多速率更新；
- 接触阶段提高内部求解率；
- 稀疏耦合；
- 保结构降阶；
- 感知误差约束下的运行阶数选择。

禁止在性能不足时悄悄切换为另一套廉价合成器。任何质量档位都必须是同一模型的有界数值近似，并附带误差报告。

### 16.5 体积与内存

目标预算：

- Web 引擎 + 一架完整乐器压缩下载目标不超过 50 MiB；
- 超过 100 MiB 必须提供盲听收益和移动端影响证据；
- Web / 移动端稳态内存目标不超过 128 MiB；
- 桌面端稳态内存目标不超过 256 MiB；
- 模型切换产生的临时双引擎内存必须有明确上限和回收点。

预算可以因经过证明的专业音质收益而调整，但不得无测量地放宽。

## 17. 音频质量、数值与安全门槛

### 17.1 基础正确性

- 目标调律下基频误差不超过 1 cent；
- 对每个音最多检查 12 个主要 partial，但只包括同时低于参考源与目标渲染 Nyquist 上限、并留有声明分析 guard band 的有效 partial；如果有效 partial 少于 12 个，则检查全部有效 partial，禁止要求高音区产生或测量不存在的第 12 partial；
- 任何超出目标实时带宽的 partial、非线性分量或结构结论，必须使用单独声明采样率与带宽的过采样离线参考验证，并包含抗混叠和降采样检查；过采样参考不能放宽实时输出的无混叠要求；
- 相邻 MIDI velocity 的响度与频谱变化连续；
- 相邻力度不得出现超过 0.5 dB 的非预期响度跳变；
- 相邻力度不得出现超过 3% 的非预期频谱重心跳变；
- 长音无固定时长截断；
- 同音重复击键不得产生完全相同的攻击波形；
- 参数或踏板平滑不得产生非预期 click；
- 输出无持续 DC、NaN、Inf、denormal 性能退化和不受控超幅。

有效 partial 的频率、中位衰减和拍频容差由每架乐器的校准报告给出。共同带宽之外的数据必须明确标记为过采样离线证据，不能与实时 44.1/48 kHz 指标混为一谈。修改门槛必须通过 ADR 审批。

### 17.2 动态表现

必须分别验证：

- ppp、pp、mp、mf、ff、fff；
- 慢速和快速攻击；
- 相同 velocity 的不同重复状态；
- 短奏、连奏和长保持；
- 单音、八度、密集和弦与宽音域和弦；
- 低、中、高音区动态连续性。

### 17.3 踏板与共鸣

必须验证：

- 连续 pedal position 到衰减和共鸣的单调且平滑响应；
- 半踏板保持时间；
- repedal 捕获已经衰减的弦；
- flutter pedal；
- 按住未发声键时的交感共鸣；
- 全踏板和弦不会退化为普通混响；
- 制音器接触不会重置不相关弦状态。

### 17.4 空间输出

必须验证：

- 麦克风移动导致可解释的频谱、相位和延迟变化；
- 立体声和 binaural 空间稳定；
- mono fold-down 不产生严重梳状抵消；
- Grand 与 Upright 的辐射和空间身份独立；
- 房间关闭时仍保持完整琴体感。

## 18. 专业听觉验收

### 18.1 测试角色

发布候选至少应包含：

- 8 名以上高级或职业钢琴演奏者；
- 3 名以上录音、混音或音乐制作人员；
- 至少两类不同 MIDI 键盘和一类高分辨率踏板；
- 耳机、近场监听和普通消费设备。

### 18.2 演奏者评分

盲测或隐藏品牌测试必须覆盖：

- 触键—声音连接；
- 极弱奏色彩；
- 极强奏冲击；
- 动态连续性；
- 重复音；
- 长音与歌唱性；
- 半踏板和快速换踏；
- 和弦融合与交感共鸣；
- Grand / Warm / Upright 身份；
- 长时间演奏疲劳感。

目标为各核心维度中位数不低于 4/5，任何核心维度不得低于 3.5/5。未达到时不能用 EQ 或混响掩盖，必须定位到物理模型、控制器映射或空间输出层。

### 18.3 对照测试

必须与以下基准等响度比较：

- 当前 Tone.js 单力度 Salamander 路径；
- 完整多力度高品质采样钢琴；
- 合法取得的商业物理建模钢琴；
- 公开授权或委托录制的真实钢琴参考。

商业产品只允许作为听觉和工作流基准，禁止逆向、提取或拟合其专有输出。月光引擎在表现力、踏板、重复音和共鸣维度应显著优于当前 Tone.js 基线。

### 18.4 制作验收

至少使用古典独奏、流行伴奏、爵士和影视氛围四类工程验证：

- 干声能否直接使用；
- 中低频是否清楚且不浑；
- 与人声、鼓、贝斯和弦乐是否共存；
- 预设响度是否一致；
- 自动化和预设切换是否无断音；
- 离线渲染与实时渲染是否一致。

## 19. 自动化测试与持续回归

### 19.1 参考场景

仓库必须维护固定 MIDI / event corpus：

- 88 键扫描；
- 多力度单音；
- 同音重复；
- 半音阶与音阶；
- 三和弦、密集和弦和宽音域和弦；
- 踏板捕获、repedal 和 flutter；
- 按住未击键的共鸣测试；
- 低音非线性压力；
- 专业演奏片段；
- 最大复音和热稳态场景。

### 19.2 数值回归

每次 DSP 修改至少比较：

- 基频以及共同 Nyquist/guard band 内的 partial 频率；共同实时带宽之外只引用声明采样率的过采样离线参考；
- T60 和多阶段衰减；
- attack time；
- 多分辨率 STFT；
- loudness 与动态曲线；
- 立体声相关性；
- pedal transfer；
- 总能量和稳定性；
- 标量参考与 SIMD 实现误差。

### 19.3 属性和安全测试

- 被动系统无输入时能量不得自发增长；
- 极端参数仍保持稳定；
- 模型包解析器 fuzz；
- NaN / Inf 注入隔离；
- 跨平台 block size 随机化；
- 实时路径分配检测；
- 长时间 deterministic replay；
- 同一随机种子在同一目标上可重现。

### 19.4 性能回归

普通 CI 负责功能、数值和 WASM 构建。专用参考硬件负责：

- callback 分位数；
- xrun；
- 活跃模态和耦合规模；
- WASM / 原生内存；
- SIMD 路径；
- 二进制与模型包体积；
- 手机热稳态。

任何声学质量提升 PR 必须同时报告 CPU、内存、体积和误差变化。

## 20. 运行时可观测性

实时线程只能写入固定大小的统计结构或原子计数，不得打印日志。控制线程低频读取并展示：

- 当前、峰值和分位 deadline ratio；
- xrun / underrun；
- 采样率和 block size；
- 活跃琴槌、琴弦、模态和耦合数；
- 音板降阶阶数；
- 交感共鸣候选数；
- SIMD 实现；
- WASM / 原生内存；
- 模型 ID、schema 与校验和；
- 设备路由和端到端估计延迟；
- 移动设备热状态。

开发者面板必须能导出匿名性能报告，但不得在音频回调中格式化字符串或上传网络。

## 23. 与当前仓库音频实验的关系

当前 JavaScript `AcousticPianoEngine`、固定长度 `AudioBuffer` 合成和 Tone.js Salamander 播放路径只保留为：

- 历史听感参照；
- UI 和 A/B 工具；
- 回归基线；
- 迁移前的功能实验。

它们不构成正式物理建模内核的架构基础。正式 DSP 不应继续嵌在 Python 生成器和生成后的 HTML 中重复维护。

本规范 PR 只建立设计基线，不修改现有运行时、页面或声音。

## 24. 发布定义（Definition of Done）

只有同时满足以下条件，某一 Moonlight 乐器才可以称为 professional 物理建模钢琴音色：

### 24.1 架构

- 正式 DSP 全部来自统一 Rust 核心；
- Web 为 WASM + AudioWorklet；
- 移动和桌面为同一代码的原生构建；
- PCM 不经过 UI / WebView IPC；
- 模型包通过 schema、稳定性和来源验证。

### 24.2 物理行为

- 全 88 键和完整弦组；
- 非线性琴槌；
- 持久琴弦；
- 双向琴桥—音板耦合；
- 全局交感共鸣；
- 连续制音器和完整踏板；
- 独立声辐射和虚拟麦克风；
- Grand、Warm 与 Upright 具有真实独立身份。

### 24.3 可演奏性

- 动态无层级跳变；
- ppp 到 fff 都有可控音色；
- 重复音、长音、半踏板和 repedal 自然；
- 演奏者核心评分达到第 18 节门槛；
- 明显优于当前 Tone.js 基线。

### 24.4 制作能力

- 干声、现场和混音均通过；
- 预设等响度；
- 空间、相位和 mono 兼容；
- 实时与离线输出一致。

### 24.5 性能与可靠性

- 满足 deadline ratio；
- 实时线程零分配、零锁、零 I/O；
- 全压力场景无 xrun；
- Web、手机和桌面参考设备通过；
- 手机热稳态通过；
- 体积和内存符合预算或有盲听证据支持例外。

### 24.6 独立性与法律

- 数据来源完整；
- 无运行时逐音采样；
- 无商业产品资产或参数提取；
- 完成必要许可证和 FTO 审查。

任何一项未满足，都只能称为研究模型或实验音色，不能以 professional 物理建模钢琴发布。

## 25. 必须由证据决定的研究问题

以下问题不能靠偏好拍板，必须通过参考实现、声学误差、盲听和性能数据选择：

1. 琴弦使用纯模态、数字波导还是混合表示；
2. 非线性琴槌求解器及接触阶段过采样倍率；
3. 横向极化和纵向耦合的最小充分状态；
4. 音板高频密集模态的表示方法；
5. 保结构降阶算法与阶数判据；
6. 全局交感共鸣的稀疏化和多速率策略；
7. 实时状态采用 f32、混合精度或局部 f64；
8. 虚拟麦克风的辐射插值与传播模型；
9. 模型包二进制格式和版本演进；
10. Web 非 SAB 环境下最稳健的事件传输；
11. 不同设备上的有界质量自适应；
12. 商业发布可使用的数据和 prior-art 边界。

### 25.1 研究决策证据契约

任何实现不得把上述未决问题静默固化为默认算法或隐藏常量。选择进入正式内核前，必须形成可评审的 ADR 或实验记录，至少包含：

- 要验证的假设和用户可感知目标；
- 备选方案及拒绝条件；
- 使用的数据角色，并证明没有读取不可变外层测试集；
- 声学、数值稳定性、被动性和听觉指标；
- CPU、内存、模型体积、deadline ratio 和目标平台结果；
- 原型或参考实现与可重现命令；
- 决策、适用范围、已知局限和回滚条件。

如果证据不足，结论必须保持为“未决”，后续 ticket 只能实现可替换的实验 seam，不能把它描述成最终物理事实。任何阈值、算法或模型阶数的例外都必须由同样的证据记录批准。
