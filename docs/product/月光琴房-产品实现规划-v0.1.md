# 月光琴房产品实现规划

> 版本：v0.1
> 状态：阶段 0–1 已实现并通过工程验收
> 更新日期：2026-07-14
> 实现阶段：Chrome Web 产品验证，iPad 横屏优先
> 首个纵向切片：第 1 章 B1-01 至 B1-07，第 6–7 小节

---

## 1. 实现目标

当前阶段不是把设计稿继续做成更精致的静态首页，而是验证月光琴房最核心的产品假设：

> 零基础用户能否通过动态节奏、屏幕琴键、逐层提示和即时反馈，在较少人工解释的情况下完成《梦中的婚礼》第 6–7 小节双手演奏。

首轮实现完成后，用户应能走完以下闭环：

1. 从学习地图进入今天的练习；
2. 听辨第 6–7 小节；
3. 用任意键完成节奏色块挑战；
4. 找到右手目标琴键；
5. 分别完成右手与左手；
6. 练习三个双手同步点；
7. 在 75 BPM 下完成第 6–7 小节双手演奏；
8. 查看音高、节奏、时值与同步反馈；
9. 失败时进入 10–30 秒补救练习，成功后回到原关卡；
10. 保存本地进度，并能从中断位置继续。

这个闭环成立后，再扩展第 8–10 小节和后续 43 个主线关卡。

## 2. 现有代码盘点

### 2.1 可以保留的基础

- Next.js 16、React 19、TypeScript 和 vinext/Cloudflare 构建链可以继续使用；
- 当前首页已经建立月光琴房的月夜、深蓝、暖金和青色反馈语言；
- 摄影、品牌、场景和装饰类图片可以继续作为视觉资产；
- `PlayablePiano` 已具备 Web Audio 发声、电脑键盘快捷键、多指针按键和按键高亮的基础；
- 已有视觉差异脚本和像素还原记录，可继续保护首页视觉基线；
- 课程结构、43 个主线关卡和第 6–7 小节逐音数据已经形成文档依据。

### 2.2 当前仍是原型的部分

| 现状 | 产品问题 | 实现处理 |
|---|---|---|
| 乐谱是静态 PNG，播放只是 CSS 扫描线 | 没有真实事件、暂停、变速或判定 | 替换为事件驱动的动态节奏/乐谱渲染器 |
| 学习地图、目标卡、统计卡和部分控件是图片或透明热点 | 内容不能随进度更新，交互语义不真实 | 保留装饰皮肤，逐步替换为真实组件和数据 |
| 首页承担地图、练习和数据展示 | 正式练习时注意力竞争过强 | 新增沉浸式练习路由，首页只负责进入与继续 |
| 页面以 1568×1003 固定画布缩放 | 1024px 等 iPad 横屏会缩小且触控目标变窄 | 改为响应式网格和安全区适配，不再整体 transform 缩放 |
| 屏幕键盘从 C3 开始 | 第 6–7 小节左手 G2 无法触控 | 重建可配置音域键盘，首切片覆盖 G2–D5 |
| 左右手通过单选切换 | 不能支持真正双手同时演奏 | 键盘与输入层改为统一音域，手别由课程事件决定 |
| 黑键内部只用升号命名 | G 小调课程需要 B♭、E♭ 等正确拼写 | 内部用 MIDI 音高，显示层单独保存调号拼写 |
| 当前声音由振荡器合成 | 音色不像钢琴，难以判断延音和时值 | 建立本地钢琴采样器，振荡器仅作开发降级方案 |
| 没有课程数据模型和评分引擎 | 页面状态无法扩展成 43 关 | 建立独立于 UI 的内容、时间轴、输入和评分模块 |
| 数据库为空，进度没有保存 | 刷新后丢失，不能做用户验证 | 首轮采用 IndexedDB 本地保存，跨设备同步后置 |
| 测试仍针对 starter loading skeleton | 不能保护当前产品行为 | 删除过时断言，建立音乐引擎、内容和浏览器流程测试 |
| `npm` 脚本使用 POSIX 环境变量写法 | Windows 开发命令直接失败 | 改成跨平台脚本或 Node 包装脚本 |

### 2.3 不应推倒重来

当前视觉还原结果继续作为首页和品牌外壳的设计基准。实现阶段只替换功能性图片、透明热点和假数据，不重做已经确认的品牌方向、场景资产和整体气质。

## 4. 总体技术原则

### 4.1 一份音乐事件数据驱动全部能力

乐谱、色块、示范声音、判定、键盘高亮、结果页和补救练习必须读取同一份事件数据。不能分别在 CSS、音频文件、图片和评分代码中重复维护节奏。

### 4.2 音频时钟是唯一时间基准

使用 `AudioContext.currentTime` 作为练习主时钟：

- 音频按主时钟提前调度；
- 画面通过 `requestAnimationFrame` 读取同一时钟计算位置；
- 触控、键盘和 MIDI 输入统一转换到同一时间轴；
- 暂停、继续、变速和循环只修改 Transport，不各自维护计时器；
- 禁止用 CSS animation、`setInterval` 或 React state 作为音乐计时真相。

### 4.3 输入方式只是适配器

触控键盘、电脑快捷键和 Web MIDI 最终都输出同一种事件：

```ts
type PianoInputEvent = {
  note: number;          // MIDI number
  phase: "down" | "up";
  atMs: number;          // 统一高精度时间轴
  velocity?: number;
  source: "touch" | "keyboard" | "midi";
};
```

评分引擎不应知道用户来自哪种设备，只在结果记录中保存输入来源。

### 4.4 课程内容与 UI 解耦

课程定义是可验证的静态内容，不直接写进 React 组件。换皮、进入原生 iPad 或接入 MIDI 时，课程事件和评分规则应能继续复用。

### 4.5 先本地闭环，再增加服务端

首轮验证不需要账号和 D1。静态课程随应用发布，设置、进度和尝试记录写入 IndexedDB。确认教学闭环有效后，再接入身份、D1 和跨设备同步。

## 6. 音乐内容模型

### 6.1 核心对象

```ts
type ScoreEvent = {
  id: string;
  measure: number;
  beat: number;
  durationBeats: number;
  midi: number;
  spelling: "D5" | "G4" | "Bb4" | "C5" | "G2" | "D3" | "Bb3";
  hand: "left" | "right";
  finger?: 1 | 2 | 3 | 4 | 5;
  syncGroup?: string;
};

type ExerciseDefinition = {
  id: string;
  lessonId: string;
  mode: "listen" | "rhythm" | "locate" | "learn" | "follow" | "perform";
  eventIds: string[];
  tempoPercent?: number;
  visibleLayers: Array<"blocks" | "staff" | "noteNames" | "fingering" | "keyboard">;
  inputPolicy: "any-key" | "pitch" | "hands";
  passCriteria: PassCriteria;
  remediation: RemediationRule[];
};
```

### 6.2 内容校验

应用构建时自动验证：

- 每小节每只手的时值总和不超过拍号；
- MIDI 音高、显示拼写和调号一致；
- 指法只能为 1–5；
- 同步组内事件拍点相同；
- 关卡引用的事件必须存在；
- 关卡速度和通过条件合法；
- 屏幕键盘音域覆盖当前关卡所有音符；
- 43 个主线关卡 ID 唯一且顺序完整。

建议使用 TypeScript 类型加运行时 schema 校验。内容错误应在构建阶段失败，不允许进入用户练习后才发现缺音或时值错误。

### 6.3 首个内容包

第一份运行时内容只录入已经校准的第 6–7 小节：

- 16 个双手事件；
- 右手每小节“一长四短”；
- 左手每小节三个四分音符；
- 每小节三个同步组；
- B1-01 至 B1-07 七个练习定义；
- 60 BPM 和 75 BPM 两档速度；
- 不要求第 1 章踏板输入。

## 7. 练习引擎

### 7.1 Transport 状态

```text
idle → ready → countIn → playing → paused → playing → completed
                         ↘ failed/retry ↗
```

Transport 负责：

- 一次用户手势解锁音频；
- 倒数与开始时间；
- 拍点到秒的换算；
- 暂停、继续和重新开始；
- 速度变化；
- 小节循环；
- 当前播放头与完成事件。

### 7.2 视觉运动

- 判定线固定在练习区宽度的约 27%；
- 只渲染判定线前后有限时间窗口内的事件；
- 所有色块或音符放入同一个可平移图层；
- 每帧根据 Transport 时间计算图层位移；
- 暂停时画面和音频停在同一事件；
- 变速后重新计算未来事件，不拉伸已经播放的声音；
- 低性能设备可以减少装饰粒子，但不能降低判定线稳定性。

### 7.3 三种时间模式

| 模式 | 时钟行为 | 错误行为 | 首切片用途 |
|---|---|---|---|
| 学习 | 目标到线后可等待正确输入 | 按错后保留目标并给提示 | 找键、右手、左手、同步骨架 |
| 跟随 | 连续低速运行 | 记录错误，不中断整段 | 节奏色块、双手练习 |
| 演奏 | 连续运行，辅助最少 | 结束后统一复盘 | B1-07 章节成果 |

### 7.4 判定流程

1. 输入到达后，寻找时间窗口内最近的未匹配目标；
2. 检查音高或任意键规则；
3. 记录相对目标时刻的偏差；
4. 在抬键时计算保持时值；
5. 同步组完成后计算左右手落键差；
6. 超过窗口仍未匹配的目标记为漏音；
7. 关卡结束后聚合为音高、节奏、时值、同步和连续性；
8. 根据主要错误选择下一条可执行提示或补救练习。

判定窗口先配置而不是写死，首轮通过延迟诊断和真实用户数据校准。

### 7.5 补救练习

补救不是新主线关卡，而是当前练习的临时切片：

- 节奏问题：退回纯色块；
- 找键问题：缩小到 2–4 个目标键；
- 右手问题：恢复琴键高亮和全量指法；
- 左手问题：循环 `G2–D3–B♭3`；
- 同步问题：只保留三个主同步点；
- 速度问题：降低到最近稳定速度。

补救达标后回到原关卡和原进度，不重新播放整段教学。

## 8. 乐谱与音乐视觉实现

### 8.1 两层渲染

1. **节奏层：** 使用自定义 SVG 渲染圆角色块、长度、颜色、判定线和状态；
2. **标准记谱层：** 使用 VexFlow SVG 渲染谱表、音符、连线、指法和大谱表。

两个渲染器读取相同的 `ScoreEvent`，通过练习阶段改变显示层，而不是维护两份音乐内容。

### 8.2 为什么不把 MusicXML 渲染器作为核心时间轴

OpenSheetMusicDisplay 适合快速显示完整 MusicXML，也支持游标和音符着色；但其定位仍以乐谱渲染为主，不适合承担月光琴房需要的自由色块、等待模式、逐事件移动、补救切片和高频交互。它可以作为内容预览或校对工具，不作为首轮练习引擎核心。

### 8.3 音乐字体

- 首轮使用 VexFlow 支持的 SMuFL 字体完成正确记谱；
- 产品气质先通过颜色、圆角、线条粗细、指法标签和动画建立；
- 不在首轮自行绘制完整音乐字体；
- 当核心交互验证通过后，再基于 SMuFL 字形表开发月光琴房定制字体或字体子集。

## 9. 钢琴键盘与声音

### 9.1 屏幕键盘

- 首切片音域覆盖 G2–D5；
- 白键宽度根据视口计算，不再使用固定 23 键图片热点；
- 支持至少 5 个同时触点；
- 触点离开、取消、页面失焦和方向切换时必须可靠结束声音；
- 琴键状态包含默认、目标、按下、正确、错误和即将使用；
- 音名与快捷键只在当前提示层级需要时显示；
- 双手模式使用同一键盘，不通过切换组件实现。

### 9.2 桌面快捷键

保留早期原型验证过的左右手快捷键思路，但迁移到统一输入适配器。快捷键只用于桌面开发、演示和无触屏测试，不进入 iPad 的教学说明。

### 9.3 钢琴音色

- 首选本地、许可证明确的钢琴多采样；
- 首次触控后预加载当前关卡音域，避免一次下载整架钢琴；
- 用少量采样点加播放速率覆盖相邻音；
- 使用增益包络避免点击爆音；
- 为示范、用户弹奏和节拍器分别设置音量通道；
- 开发环境保留当前振荡器作为采样加载失败的降级方案。

## 10. 页面与产品流程

### 10.1 学习地图 `/`

首轮只需要真实完成以下能力：

- 显示第 1 章与当前 B1 关卡；
- 显示完成、当前和未解锁状态；
- “开始/继续练习”进入正确关卡；
- 展示真实的今日练习分钟数和最近一次结果；
- 其他导航可以保留视觉状态，但不提前建设空页面。

### 10.2 沉浸式练习 `/practice/[lessonId]`

练习页只保留：

- 顶部关卡进度、退出和声音控制；
- 中部动态节奏/乐谱与固定判定线；
- 下部屏幕键盘或节奏板；
- 当前唯一教学提示；
- 必要的暂停和重新开始。

首页的课程地图、连续天数、经验值和统计图不进入练习页。

### 10.3 结果页 `/results/[attemptId]`

结果页按优先级显示：

1. 是否完成本关目标；
2. 最影响表现的一类问题；
3. 下一次怎么改；
4. 重试、进入补救或继续下一关；
5. 音高、节奏、时值和同步的次级数据。

不先展示总分烟花，再把真正问题藏在二级页面。

### 10.4 开发诊断页 `/lab/engine`

诊断页显示：

- AudioContext、performance 和输入事件时间；
- 当前 BPM、播放头与渲染帧；
- 目标事件和实际事件时间线；
- 触控点数量与活动声音；
- 输入到声音、输入到画面反馈的延迟；
- 导入固定测试事件和导出尝试 JSON。

该页面是音乐产品实现的必要工具，不进入正式导航。

## 11. 本地数据与后续服务端

### 11.1 首轮 IndexedDB

建议三个存储集合：

| 集合 | 内容 |
|---|---|
| `settings` | 音名、音量、提示偏好、最近输入方式 |
| `progress` | 当前关卡、关卡状态、最佳成绩、提示层级 |
| `attempts` | 输入来源、速度、维度结果、困难事件、开始和结束时间 |

原始逐事件日志只保留最近若干次，长期保留聚合结果，避免数据无限增长。

### 11.2 验证数据导出

在没有账号和服务端前，开发/研究模式允许导出匿名 JSON，包含：

- 首次发声时间；
- 每关尝试次数；
- 每类错误数量；
- 补救前后改善；
- 完成 B1-07 所需总时间；
- 设备、视口、输入来源和延迟摘要。

不采集姓名、录音、精确位置或不必要的设备标识。

### 11.3 D1 接入时机

只有当以下需求真实出现时再启用 D1：

- 多名测试用户的数据需要远程汇总；
- 用户需要跨设备恢复进度；
- 需要登录后保存最佳记录；
- 需要进行版本化课程发布。

接入服务端时保持 IndexedDB 为本地缓存，不让网络波动中断练习。

## 13. 验收标准

### 13.1 功能验收

- B1-01 至 B1-07 可以按顺序完整走通；
- 暂停、继续、重试、退出和恢复不会丢失状态；
- 触控、快捷键和 MIDI 进入同一评分逻辑；
- 同一固定输入事件回放能产生相同评分结果；
- 困难点选择能定位到具体事件或同步组；
- 本地进度刷新后恢复；
- 无 MIDI 设备也能完成所有关卡。

### 13.2 音乐正确性验收

- 第 6–7 小节 16 个事件与内容校准表一致；
- 每小节右手和左手时值均为 3 拍；
- 调号显示 B♭、E♭，不错误显示为 A#、D#；
- 右手指法为 `4–1–2–4–3`，左手为 `5–3–1`；
- 三个同步点与内容校准表一致；
- 60 BPM、75 BPM 与参考速度百分比换算一致。

### 13.3 iPad 与性能验收

初始工程目标如下，最终阈值根据真机测量校准：

- 1024×768、1112×834、1194×834、1366×1024 横屏均无裁切和横向滚动；
- 主要触控目标不小于 44×44 CSS 像素；
- 五指同时按下与释放不产生卡音；
- 练习动画在目标设备上保持稳定帧率，判定线附近无可见跳动；
- 输入到声音和输入到反馈延迟均被记录并显示 p50/p95；
- 页面切后台、锁屏恢复或方向切换后不会残留声音；
- 首次用户手势后音频可靠解锁。

### 13.4 可用性验收

- 用户进入练习后能在 10 秒内理解当前唯一任务；
- 第一关不要求阅读五线谱；
- 用户能解释色块长度代表时值；
- 失败反馈能让用户说出下一次应改什么；
- 练习页不展示课程地图、经验值和统计图等干扰信息；
- 指法提示不会与音名混淆；
- 用户能明确知道自己离完成第 6–7 小节还有几步。

## 15. 主要风险与应对

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 音频、画面和判定漂移 | 同一输入在不同设备评分不同 | AudioContext 单时钟、假时钟回放、真机延迟诊断 |
| iPad 琴键太窄 | 频繁误触相邻键 | 动态音域、减少无关琴键、真机五指测试 |
| 双手遮挡反馈 | 用户只看手不看提示 | 反馈集中到判定线附近，减少底部文字 |
| 音乐字体开发拖慢 MVP | 花时间做字形但交互未验证 | 首轮使用 SMuFL/VexFlow，只定制颜色和状态 |
| 课程内容与代码重复 | 改一处导致声音和谱面不一致 | 单一事件模型与构建时内容校验 |
| 结果页数据多但不可行动 | 用户知道错了却不知道怎么改 | 每次只突出一个主要问题和一个下一步 |
| 过早建设账号和后台 | 核心练习仍不可用 | 本地优先，D1 与登录后置 |
| 功能性区域继续依赖图片 | 数据无法更新，触控热点错位 | 优先替换乐谱、键盘、地图状态和结果数据 |
| Web MIDI 被误当作 iPad 能力 | 原生阶段成本判断错误 | Web MIDI 只用于桌面验证，并记录输入来源 |
| 未授权音乐内容进入公开版本 | 发布风险 | 验证期内部使用，公开发布前重新确认授权 |

## 16. 技术选型结论

| 领域 | 首轮选择 | 说明 |
|---|---|---|
| 应用框架 | 保留 Next.js/React/vinext | 当前构建链可用，不因 MVP 重写框架 |
| 时间轴 | 原生 Web Audio `AudioContext` | 作为声音、动画和评分的共同时间基准 |
| 节奏层 | 自定义 SVG | 适合圆角色块、状态、固定线与响应式布局 |
| 标准乐谱 | VexFlow SVG + SMuFL 字体 | 直接控制小节、音符颜色、指法和大谱表 |
| 完整 MusicXML 预览 | OSMD，仅作工具 | 可用于内容校对，不承担核心交互时间轴 |
| 状态管理 | 纯 TypeScript 状态机 + React context | 首轮不引入全局状态框架 |
| 内容校验 | TypeScript + 运行时 schema | 构建阶段阻止错误课程进入产品 |
| 音色 | 本地许可明确的钢琴采样 | 按当前音域分批预载，振荡器降级 |
| 本地数据 | IndexedDB | 保存设置、进度与尝试，支持离线 |
| 服务端 | 暂不启用；后续 D1 | 用户验证与跨设备需求成立后再接入 |
| 自动化 | 单元 + 假时钟集成 + 浏览器流程 | 真机多点触控保留人工验收 |

技术依据：

- [VexFlow](https://github.com/vexflow/vexflow) 是面向 Web 的 TypeScript 音乐记谱渲染库；
- [OpenSheetMusicDisplay](https://github.com/opensheetmusicdisplay/opensheetmusicdisplay) 适合 MusicXML 显示，但官方也明确说明它是渲染器而非完整交互编辑器；
- [Web MIDI API](https://developer.mozilla.org/en-US/docs/Web/API/Web_MIDI_API) 仍属于有限可用能力并要求安全上下文，因此只作为桌面 Chrome 增强输入；
- Web Audio 精确调度原则可参考 [Tone.js Transport 官方说明](https://github.com/Tonejs/Tone.js/wiki/Transport)，本项目首轮在自有 Transport 中直接采用同一类 AudioContext 时间调度方式。
